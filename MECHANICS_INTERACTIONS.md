# Мультиплеер: как механики взаимодействуют между собой

Этот документ описывает **стыки** механик, а не сами механики. Правила отдельных
систем живут в `GAME_MECHANICS.md` (§1–§12 — контракт мода, §13–§16 — канон игры);
числа AI — в `docs/rake-ai-flow.md`; история рефакторинга — в
`docs/architecture/2026-11-17-stability-plan.md`.

Зачем он нужен:

1. **Сверка с реализацией.** Каждое правило имеет ID (`I-*`) и проверку — можно
   пройтись по коду и отметить «выполняется / нарушается».
2. **Проектирование.** Из правил выводятся границы модулей (§9): если механика
   нарушает правило взаимодействия, значит граница проведена не там.
3. **Приёмка.** Сценарии §7 — это то, что должно проходить в живой игре, независимо
   от того, как устроен код.

Формат правила: **ID — формулировка — чем проверяется**. Числа в двух документах
могут расходиться; расхождения собраны в §11 и считаются дефектом документации,
а не «двумя правдами».

## 1. Принципы сосуществования (P1–P10)

- **P1. Один владелец.** У каждого состояния ровно одна система-владелец; все
  остальные читают. Два владельца = гарантированный рассинхрон.
- **P2. Хост — истина, клиент — ввод и картинка.** Клиент не мутирует мир: он шлёт
  намерение, хост применяет и рассылает результат (§9 в `GAME_MECHANICS.md`).
- **P3. Порядок важнее содержания.** Один и тот же набор событий в разном порядке
  даёт разный мир. Порядок фиксирован конвейером §3.
- **P4. Изменение = событие.** Не «поправить поле», а «событие → валидация →
  применение → репликация». Событие идемпотентно по ключу.
- **P5. Смерть терминальна.** Умерший игрок перестаёт быть участником симуляции
  в этом тике; его действия, отправленные до смерти, но применённые после — отменяются,
  кроме уже нанесённого урона.
- **P6. Фаза — граница мира.** День и ночь — разные сцены (`Application.LoadLevel`).
  Всё, что должно пережить границу, обязано быть сохранено **до** загрузки и
  восстановлено **до** первого кадра симуляции.
- **P7. Отказ деградирует, не зависает.** Потеря связи, недостижимая цель, битый
  пакет — это состояние, а не исключение; система обязана прийти в определённое
  состояние (Idle, меню, AI), а не в «полуживое».
- **P8. Презентация ничего не решает.** UI/HUD/меню читают снимок состояния и не
  могут оживить, убить, снять стан или выдать предмет.
- **P9. Числа живут в одном месте.** Если лимит/таймер продублирован в двух файлах,
  рано или поздно они разойдутся (§11 — уже разошлись).
- **P10. Всё проверяемо.** У каждого правила есть наблюдаемый признак; если признака
  нет — правило нельзя считать выполненным.

## 2. Владение состоянием

| Система | Владеет | Где в коде | Кто читает | Запрещено |
|---|---|---|---|---|
| Сессия | state, номер ночи, победа | `Core/SessionManager.cs`, `Core/MatchState.cs` | все | клиент меняет состояние |
| Фаза | current phase, таймер, ночь | `Core/DayNightManager.cs` | AI, HUD, мир | менять фазу из домена предметов/боя |
| Граница сцены | снимок мира | `Core/WorldPersistence.cs`, `Core/MultiplayerSceneManager.cs` | все | терять состояние при `LoadLevel` |
| Игрок | HP, позиция, инвентарь, фонарь | `Components/NetworkedPlayer.cs`, `MatchState.PlayerHealth` | HUD, AI, бой | клиент пишет себе HP/позицию |
| Рейк-AI | состояние, цель, снапшот | `Components/NetworkedRakeAI.cs` | HUD, камеры, бой | клиент симулирует Рейка |
| Рейк-игрок | намерения владельца роли | `Components/RakePlayerController.cs`, `Core/RakeControlSync.cs` | хост-AI | владелец мутирует мир напрямую |
| Бой | урон, снаряды | `Core/ProjectileSystem.cs`, `Core/RakeNetworkManager*.cs` | HUD | второй канал урона (ванильный raycast) |
| Смерть | dead set, таймеры респавна | `Core/PlayerDeathSystem.cs`, `MatchState` | лут, HUD | респавн без хоста |
| Предметы | существование и владелец | `Components/NetworkedItem.cs`, `Patches/ItemPickupSync.cs` | все | два владельца одного предмета |
| Камеры | 5 слотов, состояние | `Components/NetworkedCameraSystem.cs` | Рейк, HUD | камера, пережившая матч |
| Капканы | armed/triggered | `Components/NetworkedTrap.cs` | Рейк, бой | повторный триггер |
| Двери | открыта/закрыта | `Components/NetworkedDoor.cs`, `Core/DoorSync.cs` | все | клиент открывает дверь себе |
| Животные | позиция, паника | `Components/NetworkedPig.cs` | камеры, урон | — |
| Сеть | соединения, seq | `Networking/*` | все | домен лезет в сокет напрямую |
| UI | **ничего** | `UI/*.cs` | снимок состояния | быть источником истины |

Правило вывода: если системе нужно поле, которым она не владеет, она **читает его из
снимка** или **просит владельца событием**. Прямая запись в чужое поле — нарушение P1.

## 3. Конвейер тика хоста

Порядок фиксирован. Каждый шаг видит только результат предыдущих; шаг не может
заглядывать вперёд и не может менять решения более раннего шага.

```text
┌─ 1. GATE ──────────────── матч идёт? игрок жив? (иначе — выход)
├─ 2. PHASE TIMER ───────── таймер фазы; истёк → очередь перехода (не внутри тика)
├─ 3. INBOX ─────────────── приём пакетов в порядке (клиент, seq)
├─ 4. VALIDATE ──────────── границы мира, NaN, частота, права; отказ → счётчик
├─ 5. MOVE ──────────────── применение ввода клиентов к их персонажам
├─ 6. INTERACT ──────────── подбор, дверь, поставить/снять камеру, капкан
├─ 7. RAKE ──────────────── AI Рейка (или снапшот игрока-Рейка) + восприятие
├─ 8. ATTACK ────────────── замах/удар Рейка, выстрелы, снаряды
├─ 9. DAMAGE ────────────── применение урона; проверка смерти
├─ 10. DEATH ────────────── рагдолл, лут, постановка таймера респавна
├─ 11. RESPAWN ──────────── истёкшие таймеры → возрождение
├─ 12. REPLICATE ────────── рассылка изменений (dirty) с их частотами
└─ 13. PRESENT ──────────── HUD/UI из снимка; ничего не мутирует
```

Правила конвейера:

- **I-TICK-1.** Шаги 5–11 не могут менять фазу. Переход ставится в очередь на шаге 2
  и исполняется после шага 12 — текущий тик доигрывается целиком.
- **I-TICK-2.** Смерть (шаг 9/10) наступает в том же тике, но накопленный урон не
  откатывается: сначала применяются все попадания, уже начатые в тике, затем
  фиксируется смерть. Урон, пришедший **после** смерти цели, не начисляется — overkill
  отбрасывается осознанно (так и работает код, см. §10.3).
- **I-TICK-3.** Шаг 6 не может создать предмет/камеру, которую шаг 12 не сможет
  описать снапшотом (нет snapshot-поля → нет события).
- **I-TICK-4.** Шаг 3 соблюдает порядок пакетов одного клиента; между клиентами
  порядок — по времени прибытия (кто первый, того и предмет). Перестановка ради
  «справедливости» запрещена.
- **I-TICK-5.** Если шаг выбросил исключение, тик не прерывается: система логирует
  один раз и переходит в определённое состояние (P7).
- **I-TICK-6.** Клиент выполняет только шаги 1, 5 (предсказание себя), 12 (применение)
  и 13 (презентация). Остальные шаги на клиенте не существуют.

## 4. Временные шкалы и бюджеты

| Что | Значение | Источник | Следствие для взаимодействий |
|---|---|---|---|
| Длительность фазы | 300 с (день и ночь 1) | `DayNightManager.DayDuration/NightDuration` | таймер — только у хоста; клиент получает остаток |
| «Поздние» ночи | 1800 с (ночи 2–3) | `LateNightDuration` | осознанное изменение 1.1.16, не расхождение |
| Смена фазы | `LoadLevel` + межсценовая пауза | `DayNightManager.LoadLevelForPhase` | мир переживает только через `WorldPersistence` |
| Снапшот Рейка | 15 Гц | `syncRate = 0.066` | 3–4 тика между снапшотами — интерполяция обязательна |
| Состояние игрока | ~20 Гц | контракт §9 | ввод идёт чаще состояния; хост применяет ввод, не гоняет состояние назад |
| Замах удара Рейка | 1.2 с (код) / 0.7 с (контракт) | `AttackWindup` | **расхождение**, §11 |
| Восстановление после удара | 2.0 с (код, `AttackRecovery`) / 5 с (код, `_attackCooldown`) / 2.0 с (контракт) | `NetworkedRakeAI` | **расхождение**, §11 |
| Промах (не достал) | 1 с | `_attackCooldown = 1f` | промах не блокирует следующий замах надолго |
| Кулдаун после урона по игроку-Рейку | 10 с | комментарий в `NetworkedRakeAI` | игрок-Рейк не «долбит» без окна |
| Стан от капкана | 3 с | контракт §4 | стан перекрывает AI-состояние, не отменяет урон |
| Смерть → респавн | 8 с | `PlayerDeathSystem.RespawnDelay` | таймер живёт в `MatchState`, не в компоненте |
| Заморозка трупа | 5 с | контракт §8 | после — труп декорация |
| Пауза между заходами AI | 20–35 с | `lurkIntervalMin/Max` | не сбрасывается при отвлечении шумом (изменение 1.1.17) |
| Первая задача ночи | 5–10 с | `_lurkCooldownTimer = Range(5,10)` | ночь не начинается с мгновенной атаки |
| Шум выстрела | кулдаун 6 с, слышно 300 м | `_noiseCooldown`, `noiseHearRange` | выстрел — глобальный триггер интереса, а не локальный |
| Слоты камер | 5 | контракт §4/§5 | шестая камера запрещена, а не «вытесняет» первую |

Все длительности живут в одном месте и приходят в код из конфигурации; дубли в
нескольких местах запрещены (P9).

## 5. Матрица взаимодействий

### 5.1 Фаза ↔ мир

- **I-PHASE-1.** Переход фазы сохраняет: камеры и их состояние, капканы (поставленные
  и сработавшие), инвентарь каждого игрока, потреблённые предметы мира, HP Рейка.
- **I-PHASE-2.** Переход фазы **не** сохраняет: трупы, таймеры респавна, состояние
  погони, стан, эффекты HUD.
- **I-PHASE-3.** Восстановление идёт строго в порядке: сцена → `WorldPersistence.Restore`
  → спавн игроков → AI → HUD. HUD, поднятый раньше мира, показывает чужие значения.
- **I-PHASE-4.** Камеры/капканы одной фазы не появляются в другой, если их не было:
  восстановление не «досыпает» недостающее.
- **I-PHASE-5.** Камера, поставленная в последний тик фазы, либо попала в снимок
  целиком, либо не существует. Полусостояния «слот занят, объекта нет» запрещены.
- **I-PHASE-6.** Смена фазы не наносит урон и не лечит; HP переносится как есть,
  кроме явного правила «новая сцена оживляет всех» (§11, решение №6).

### 5.2 Фаза ↔ игроки и бой

- **I-PHASE-7.** Фаза не меняется в середине боя: очередь перехода исполняется после
  тика, поэтому удар, начатый в этом тике, доигрывается, а следующий замах — уже нет.
- **I-PHASE-8.** При уходе в день Рейк завершает заход (`FinishEncounter`), а не
  «зависает в Chase»; пауза между заходами не начинается заново.
- **I-PHASE-9.** Стан/замедление/капкан сбрасываются на границе фазы: новая сцена —
  новые сущности.
- **I-PHASE-10.** Таймер фазы не переживает реконнект: клиент при подключении получает
  остаток и номер ночи из `SessionState`/`PhaseChange`, а не считает локально.
- **I-PHASE-11.** «Пропустить день/ночь» из ванильного диалога в трейлере
  (`LevelSkip.SkipLevel`) — это **намерение**, а не локальная загрузка уровня: хост
  ставит переход в очередь, клиент отправляет `PhaseSkipRequest`. Локальный
  `Application.LoadLevel` из диалога запрещён на всех пирах — иначе фаза сдвигается
  только у одного игрока.
- **I-PHASE-12.** Хост сообщает смену уровня **именем сцены**, а не индексом из
  `Application.loadedLevel`: в этой сборке `LoadLevel` применяет сцену на следующем
  кадре, поэтому сразу после вызова индекс ещё старый. Устаревший индекс клиент
  отбрасывает как «уже загружено», и он отстаёт на одну фазу.

### 5.3 Рейк ↔ окружение

- **I-RAKE-1.** Камера: Рейк ломает ближайшую поставленную камеру в радиусе ~2.5 м
  (проверка раз в ~0.5 с). Сломанная камера освобождает слот и реплицируется как
  событие; клиент не может «починить» камеру.
- **I-RAKE-2.** Освобождение слота и разрушение — одно событие. Слот не может быть
  свободен, а объект жив (и наоборот).
- **I-RAKE-3.** Капкан: срабатывание один раз на сущность, ставит Рейка в стан на 3 с.
  Повторное срабатывание тем же капканом запрещено (идемпотентность P4).
- **I-RAKE-4.** Урон от капкана по Рейку — **не определён** контрактом (в ванили ранил,
  в коде — только стан). Решение в §11 п.4; до решения считается «нет урона».
- **I-RAKE-5.** Животное: урон от капкана 100, смерть животного синхронизируется;
  животные не ломают камеры и не считаются «движением Рейка» (только вспышка камеры).
- **I-RAKE-6.** Шум: выстрел слышен до 300 м и запускает интерес, если у Рейка нет
  активного захода; кулдаун 6 с, чтобы очередь выстрелов не превращалась в «магнит».
- **I-RAKE-7.** Свет фонаря влияет на восприятие, но не на урон и не на фазу; выключение
  фонаря не отменяет уже начатый заход.
- **I-RAKE-8.** Двери: может ли Рейк открывать дверь — **не определено** (§11 п.5).
  До решения двери для него — препятствие, а не проходимый объект.

### 5.4 Игрок-Рейк ↔ AI ↔ отключение

- **I-ROLE-1.** Роль Рейка одна. Захват роли останавливает AI в текущем состоянии:
  позиция/HP/цель сохраняются, паузы не сбрасываются.
- **I-ROLE-2.** Пока роль у игрока, его тело-охотник не существует в мире: нельзя
  «два тела», нельзя подобрать предмет «за Рейка».
- **I-ROLE-3.** Атака игрока-Рейка — это `RakeAttackRequest`, а не прямой урон.
  Хост проверяет дистанцию, цель, кулдаун; игрок не может нанести урон «по факту клика».
- **I-ROLE-4.** Отключение владельца роли возвращает управление AI **в том же
  состоянии** (не в Idle), с сохранением HP и позиции.
- **I-ROLE-5.** Захват/возврат роли не меняет фазу и не лечит/не ранит Рейка.
- **I-ROLE-6.** Клиенты видят позу/анимацию игрока-Рейка; при возврате к AI анимация
  переключается без «рывка» позиции.

### 5.5 Урон ↔ всё

- **I-DMG-1.** Один канал: `FireRequest` → валидация хоста → снаряд (`ProjectileSystem`)
  → `DamageApplied`. Ванильный raycast на хосте выключен — иначе двойной урон.
- **I-DMG-2.** PvP: попадание в живого охотника наносит урон и отбрасывает рагдолл;
  в труп, в себя, в «лежачего бесконечно» — нет.
- **I-DMG-3.** Удар Рейка: 10 урона, не сквозь стену, не по мёртвым; замах прерывается
  смертью цели и не переносится на другую цель.
- **I-DMG-4.** Один снаряд учитывается один раз (ключ снаряда); повторная доставка
  `DamageApplied` не добавляет урон.
- **I-DMG-5.** Урон не откатывается смертью стрелка: если попадание случилось раньше
  смерти в конвейере — оно остаётся (P5, I-TICK-2).
- **I-DMG-6.** Урон по окружению (окно, животное) считается один раз и не дублируется
  между «ванильным» и мод-каналом.

### 5.6 Смерть ↔ лут ↔ респавн

- **I-DEATH-1.** Смерть отключает управление, но не отключает приём событий: труп
  остаётся сущностью мира.
- **I-DEATH-2.** Инвентарь рассыпается вокруг трупа; каждый предмет становится
  «свободным» один раз; дубликаты запрещены.
- **I-DEATH-3.** Труп замораживается через 5 с и живёт до конца матча; смена фазы труп
  не переносит (I-PHASE-2).
- **I-DEATH-4.** Респавн через 8 с, HP 100, точка — серверная (не место смерти, не
  геометрия, не «под Рейком»).
- **I-DEATH-5.** Респавн не воскрешает подобранные/потраченные предметы и не
  восстанавливает камеры.
- **I-DEATH-6.** Смерть последнего живого охотника = конец матча; смерть при живых
  союзниках матч не завершает.
- **I-DEATH-7.** Смерть игрока-Рейка завершает матч победой охотников (`RakeDied`), а не
  «респавнит Рейка».

### 5.7 Предметы ↔ поздний вход ↔ сцена

- **I-ITEM-1.** Предмет существует в мире в одном экземпляре; подбор — арбитраж хоста
  по первому прибывшему пакету; второй получает отказ (`ItemPickupConfirm` / нет).
- **I-ITEM-2.** Поздний вход получает полный снимок: живые предметы, состояние камер,
  дверей, капканов, HP. Сцена при этом **не перезагружается**.
- **I-ITEM-3.** Подобранный/использованный предмет не появляется после смены фазы.
- **I-ITEM-4.** Ящик камер — стопка: каждое взятие уменьшает `count`; на нуле ящик
  исчезает; отрицательный `count` невозможен.
- **I-ITEM-5.** Предмет, выброшенный из инвентаря, становится свободным и не может
  остаться «привязанным» к прежнему владельцу.

### 5.8 Сеть ↔ всё

- **I-NET-1.** Любая мутация мира инициируется хостом; клиентский пакет — это
  намерение, а не приказ.
- **I-NET-2.** Персистентные события (подбор, установка, смена роли, разрушение)
  идемпотентны по ID; потеря пакета лечится повторной доставкой или снапшотом.
- **I-NET-3.** Реконнект восстанавливает роль и состояние из снимка; «второй» игрок
  не создаётся.
- **I-NET-4.** Обрыв хоста = конец матча у всех; клиент не продолжает «один в мире».
- **I-NET-5.** Смена фазы рассылается как событие до `LoadLevel`; клиент, не
  получивший её, догоняет по снапшоту, а не по локальному таймеру.
- **I-NET-6.** Версия протокола проверяется в handshake; несовпадение — явный отказ
  (`ProtocolReject`), а не «странное поведение».

### 5.9 UI ↔ состояние

- **I-UI-1.** HUD читает: фазу, ночь, таймер, HP Рейка, HP игрока, слоты камер. Ничего
  не пишет.
- **I-UI-2.** HP-бар Рейка обновляется из состояния сессии при каждом изменении, а не
  по таймеру «авось».
- **I-UI-3.** Tab (камеры), F3 (карта) — локальные операции; они не требуют хоста и не
  создают событий мира.
- **I-UI-4.** Меню/консоль/пауза не могут «оживить» игрока, снять стан или выдать
  предмет; отладочные команды — только через явные серверные вызовы.

### 5.10 Рейк ↔ охотник: темп атак (анти-станлок)

- **I-RAKE-9.** После попадания задача Рейка **немедленно** становится `Flee`
  (а не `Chase`): он уходит, а не стоит над рагдоллом и не бьёт, как только тот
  встанет.
- **I-RAKE-10.** Один и тот же охотник не может быть ранен чаще, чем раз в
  `reHitInterval` (9 с), независимо от состояния Рейка.
- **I-RAKE-11.** После вставания из рагдолла действует пауза `postGetUpGrace` (2.5 с):
  в это время атака по этому охотнику запрещена.
- **I-RAKE-12.** После попадания Рейк не берёт того же охотника в погоню
  `disengage`-окно (~7 с), даже если тот стоит вплотную: `Idle` не переходит в `Chase`
  по близкой дистанции раньше этого срока.
- **I-RAKE-13.** `Flee` завершается по достижении `fleeStopDistance` (100 м) или по
  таймауту; точка отхода обязана быть на NavMesh и не ближе 25 м к охотнику, иначе
  задача завершается, а не превращается в «бег на месте».

## 6. Приоритеты конфликтов

Если два правила претендуют на один и тот же объект в одном тике, побеждает то, что
выше:

| Приоритет | Что | Пример |
|---|---|---|
| **0** | Конец матча | матч закончился — ни урон, ни подбор, ни респавн не исполняются |
| **1** | Смерть игрока | умерший не подбирает и не стреляет, даже если пакет пришёл раньше |
| **2** | Смена фазы (очередь) | тик доигрывается, затем сцена; фаза не отменяет уже нанесённый урон |
| **3** | Урон и его следствия | стан/удар/попадание применяются до смерти и до фазы |
| **4** | Арбитраж хоста по объектам | предмет уходит первому, второй получает отказ |
| **5** | Владение ролью | роль Рейка перекрывает AI, пока жива |
| **6** | Презентация | HUD обновляется последним и ничего не решает |

Правило: конфликт разрешается **один раз** и фиксируется событием. «Перерешение» того
же конфликта в следующем тике — источник мерцающего состояния.

## 7. Сценарии (что должно происходить)

### 7.1 День: камера + капкан (хост и клиент)

1. Клиент жмёт «поставить камеру» → `CameraSetupRequest` с позицией/направлением.
2. Хост проверяет: свободный слот (≤5), допустимая точка, дистанция.
3. Хост создаёт камеру, атомарно помечает слот, рассылает `CameraSpawn`.
4. Клиент получает `CameraSpawn` в том же порядке, что и остальные пиры.

**Проверка:** 6-я камера отвергнута; слот и объект появляются/исчезают одновременно;
после смены фазы камера на месте, слот занят.

### 7.2 Ночь: камера сломана, капкан сработал

1. Рейк подходит к камере → через ≤0.5 с `CameraDestroy`.
2. Клиенты убирают камеру и освобождают слот; HUD показывает 4/5.
3. Рейк наступает на капкан → стан 3 с, капкан одноразовый (`TrapState` triggered).
4. Игрок видит в фиде «камеры нет», а не «камера есть, но пустая».

**Проверка:** повторный проход по тому же капкану не станит; слот не «залипает».

### 7.3 Выстрел клиента → смерть → лут → респавн

1. Клиент: `FireRequest` (позиция, направление, оружие).
2. Хост валидирует и создаёт снаряд; рассылает `FireVisuals`.
3. Попадание → `DamageApplied`; HP в `MatchState` уменьшается.
4. HP ≤ 0 → `PlayerDied`; рагдолл у всех; инвентарь — лут (один раз).
5. Через 8 с `PlayerRespawn`; позиция — серверная точка.

**Проверка:** урон не задваивается; лут нельзя подобрать дважды; после респавна
инвентарь пуст; стрелок, умерший после попадания, урон не «отменяет».

### 7.4 PvP днём

1. A стреляет в B; B получает урон и отбрасывание.
2. B умирает → лут → таймер.
3. Матч продолжается (если живы другие).

**Проверка:** попадание в труп не наносит урон; в себя — невозможно; «бесконечное»
добивание лежачего запрещено.

### 7.5 Смена фазы во время погони

1. Таймер фазы истёк в тике N.
2. Тик N доигрывается: замах доходит или не доходит, но новых действий не начинается.
3. `FinishEncounter` → Рейк паркуется; `WorldPersistence.SaveWorld` (камеры, капканы,
   инвентарь, HP).
4. `LoadLevel` новой сцены.
5. `RestoreWorld` → спавн игроков → AI → HUD.

**Проверка:** после загрузки состав камер/капканов совпадает с моментом до перехода;
никто не «умер от фазы»; трупы исчезли; таймер ночи корректен.

### 7.6 Захват роли Рейка посреди ночи

1. Игрок берёт роль → `RakeRoleRequest` → `RakeOwner`.
2. AI останавливается в текущем состоянии (HP/позиция/цель).
3. Игрок атакует только через `RakeAttackRequest`; хост валидирует.
4. Отключение игрока → AI продолжает с того же места.

**Проверка:** нет второго тела; тело-охотник не подбирает предметы; при возврате к AI
позиция не «телепортируется»; кулдаун не обнуляется.

### 7.7 Поздний вход ночью

1. Клиент подключается → handshake (версия протокола) → полный снимок.
2. Клиент видит: всех игроков, камеры, капканы, двери, живые предметы, HP Рейка.
3. Сцена не перезагружается; чужих предметов (уже подобранных) нет.

**Проверка:** после входа нет «призраков» предметов; новый игрок не может взять то,
что уже взято; его действия не ломают таймер фазы.

### 7.8 Обрыв связи

1. Клиент пропал → хост помечает соединение, игрок переходит в определённое состояние.
2. Если это владелец роли Рейка — роль возвращается AI.
3. Хост пропал → у клиентов конец матча, выход в меню, без «одиночной игры».

**Проверка:** нет зависших лобби и «мёртвых» прокси; повторный вход снова работает.

## 8. Машины состояний (стыки)

```text
Матч:     Waiting ──start──▶ Active ──victory/defeat──▶ GameOver ──▶ Waiting
Фаза:     Day ──timer──▶ Night ──timer──▶ Day ... (3 ночи) ──▶ GameOver
Игрок:    Alive ──hp<=0──▶ Dead ──8s──▶ Respawning ──▶ Alive
Рейк-актор: AI ──role taken──▶ Controlled ──owner lost──▶ AI
          AI: Idle → Lurk → Stealth → Chase → Attack → (после захода) Idle
Камера:   Empty ──place──▶ Placed ──destroyed──▶ Empty
Капкан:   Armed ──step──▶ Triggered ──▶ Used (одноразовый)
Предмет:  InWorld ──pickup──▶ Carried ──drop/use──▶ InWorld/Consumed
```

Стыки:

- **I-SM-1.** `Dead` и `GameOver` — терминальные: пока они не сняты, события подбора и
  атаки игнорируются.
- **I-SM-2.** Переход `AI → Controlled` и обратно не сбрасывает HP, позицию и таймеры.
- **I-SM-3.** Переход камеры `Placed → Empty` — это одно событие (слот + объект).
- **I-SM-4.** Переход предмета `Carried → InWorld` (выброс) и `Carried → Consumed`
  (использование) идут через хост, даже если инициатор — клиент.
- **I-SM-5.** Переход фазы не является переходом состояния игрока: он лишь сбрасывает
  смерть/респавн по правилу I-PHASE-6.

## 9. Архитектура, следующая из правил

### 9.1 Слои и направления зависимостей

```text
┌──────────────────────────────────────────────┐
│ UI / HUD / меню        (только чтение)       │  UI/*
├──────────────────────────────────────────────┤
│ Presentation (модели, эффекты, звук)         │  Components/Remote*, UI/*
├──────────────────────────────────────────────┤
│ Domain (сессия, фаза, игроки, Рейк, бой,     │  Core/RakeNetworkManager.*.cs
│         предметы, камеры, капканы, двери)    │  Core/{Session,DayNight,Death}*.cs
├──────────────────────────────────────────────┤
│ State (MatchState, WorldPersistence)         │  Core/MatchState.cs
├──────────────────────────────────────────────┤
│ Protocol (пакеты, сериализация, версия)      │  Networking/*
├──────────────────────────────────────────────┤
│ Transport (Telepathy TCP / Steam P2P)        │  Networking/Transport*, Steam*
└──────────────────────────────────────────────┘
```

- **I-ARCH-1.** Зависимости идут только вниз. Domain не знает про UI; Transport не
  знает про домен.
- **I-ARCH-2.** Домен получает пакет, валидирует и вызывает **сервис**, а не пишет в
  `UnityEngine`-объекты напрямую. Иначе появляется «бог-класс» (уже был).
- **I-ARCH-3.** Состояние матча — только в `MatchState`; состояние сцены — только в
  `WorldPersistence`. Статических полей «на матч» быть не должно.
- **I-ARCH-4.** Ни одного статического счётчика, переживающего матч (`NextNetId` и
  подобные) — иначе новый матч продолжает старый.
- **I-ARCH-5.** Один домен = один файл/партиал и один диспетчер; обработчик пакета не
  длиннее «валидация + вызов сервиса».
- **I-ARCH-6.** Снимок мира — сериализуемый объект, из которого можно собрать клиента
  с нуля. Нет снимка — нет позднего входа (I-ITEM-2).
- **I-ARCH-7.** Каждый переход состояния проходит через `Invariants` в dev-сборке:
  фаза == загруженная сцена, матч активен ⇒ сцена ≥ 1, id игрока из пакета существует.
- **I-ARCH-8.** `Safe.Run` на всех внешних вызовах: ошибка логируется один раз и
  считается, а не глотается.

### 9.2 Границы доменов

| Домен | Файл(ы) | Что не должен делать |
|---|---|---|
| Session | `RakeNetworkManager.Session.cs`, `SessionManager` | считать урон |
| Phase | `DayNightManager`, `MultiplayerSceneManager` | спавнить игроков иначе как через порядок I-PHASE-3 |
| Players | `RakeNetworkManager.Players.cs` | решать судьбу предметов |
| Rake | `RakeNetworkManager.Rake.cs`, `NetworkedRakeAI` | начислять урон игрокам напрямую |
| Combat | `ProjectileSystem`, `RakeNetworkManager` (damage) | менять инвентарь |
| Items | `RakeNetworkManager.Items.cs`, `ItemPickupSync` | сменять фазу |
| Cameras | `RakeNetworkManager.Cameras.cs`, `NetworkedCameraSystem` | ломать себя (только Рейк/хост) |
| World | `RakeNetworkManager.World.cs`, `NetworkedTrap`, `NetworkedDoor` | владеть HP игрока |

### 9.3 Порядок инициализации сцены

```text
MatchState (Begin/SetLevel)
  → WorldPersistence.Restore
  → PlayerSpawner (живые, HP из MatchState)
  → NetworkedRakeAI (состояние из снимка, HP)
  → HUD/UI (последним, только чтение)
```

Нарушение порядка = «HUD показывает ночь днём», «камера-призрак», «первый кадр без
мира» — самые частые визуальные баги.

### 10.3 Уточнения к первым выводам

Аудит шёл в три прохода, и два «страшных» вывода при прямой проверке оказались мягче:

- **HP Рейка не константа 100.** `SessionManager._rakeHealth` поллится из ванильного
  `Enemy_AI.Health` раз в 0.25 с (`SessionManager.cs:265–288`), и `ApplyPersistentRakeHealth`
  восстанавливает актуальное значение. Проблемы две: `WorldPersistence.SavedRakeHealth`
  — мёртвый код (никто не читает), а при отсутствии `Enemy_AI` работает fallback 100
  (`NetworkedRakeAI.cs:3329–3332`).
- **Сломанную камеру снимают клиенты, а не хост.** `HandleCameraDestroy`
  (`NetworkedCameraSystem.cs:696–708`) вызывает `ApplyUnsetupVisuals`, а серверный
  `BreakCamera` — нет. Поэтому расхождение видно именно у хоста.
- **Смерть в тике терминальна** — остаток дроби по уже умершей цели не начисляется.
  Это осознанное правило (без overkill), а не потеря урона; контракт I-TICK-2 уточнён
  под фактическое поведение.

### 10.6 Проверка в живой игре (MCP, 20.11.2026)

Мост поднимается флагом: `Rake.exe -batchmode -rakemcp` → `http://127.0.0.1:8765`
(работает и в batch-режиме, скриншоты там чёрные, состояние/UI/клики — нет).

Сценарий проверки:

1. `/menu?screen=host` → `/click?name=HostGameBtn` → `/click?name=LanHostBtn` →
   `/click?name=StartGameBtn` — матч на `Level_1(Day)`.
2. `/phase?skip=1` дважды: `Day → Night → Day`.
3. После каждого перехода — `/state` и хвост `BepInEx/LogOutput.log`.

| Проверка | Результат |
|---|---|
| Сцена и фаза | `Level_1(Day)` → `Level_1(Night)` → `Level_1(Day)`, `phaseMatchesLevel=true` |
| Матч | `matchActive=true` на всех переходах |
| Инварианты | `invariants=0` |
| Восстановление мира | ровно одна строка `[4.4] World snapshot applied for level N (scene entry)` на уровень |
| HP Рейка | `[4.5] Rake health carried over: 2500.0` на каждом переходе |
| Камеры | `[4.4] World saved: cameras=19` |
| Исключения | в `LogOutput.log` нет |
| Целостность установки | `[Integrity] 31 files match the manifest` |

Что это доказывает: переход фазы больше не рвёт тик (иначе `phaseMatchesLevel` и матч
сломались бы на втором переходе), снапшот применяется один раз, HP Рейка переживает
рассвет.

Что **не** проверено: два клиента одновременно (нужен второй экземпляр), урон и капканы
под нагрузкой, квота камер при сломе, респавн рядом с Рейком.

### 10.7 Двухпроцессная проверка (20.11.2026)

Две копии игры на одной машине: хост с мостом на 8765, клиент — на 8766
(`GameBridgePort` в `com.rake.multiplayer.cfg`). Сценарий: хост создаёт LAN-матч →
клиент подключается к идущему матчу → два скипа фазы подряд.

| Проверка | Результат |
|---|---|
| handshake | лог хоста `C1 handshake ok (protocol 3)`, у обоих `/state` `protocol:3` |
| поздний вход | клиент загрузил уровень после handshake, `matchActive:true` |
| скип фазы | оба: `Level_1(Day)` → `Level_1(Night)` → `Level_1(Day)`, `phaseMatchesLevel:true`, инварианты 0 |
| скип с клиента | `forwarded:true`, лог `C1 asked to skip the phase`, оба на одной фазе |
| целостность | `31 files match the manifest` |

Тест нашёл и закрыл ещё один дефект: **клиент отставал на одну фазу** — хост рассылал
`LevelChange` с индексом, прочитанным сразу после `LoadLevel`, а сцена применяется на
следующем кадре (I-PHASE-12). Теперь переход передаётся именем сцены (`LevelChangePacket.SceneName`).

Что этим тестом не покрыто: смерть и респавн в двухпроцессном режиме (респавн через 8 с
не даёт поймать снимок мёртвого игрока), квота камер при сломе.
